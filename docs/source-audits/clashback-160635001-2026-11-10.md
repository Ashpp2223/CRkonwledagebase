## 构建身份与可定位接口

- [`vendor/crx/bindings/160635001.json`](https://github.com/ak1NaN/Clashback/blob/45c1f26b942ae1d706f2004791e73013e4330099/vendor/crx/bindings/160635001.json) 写有 `build=160635001` 与 `libg_sha256=c4721bd90f46fd1709e9dc498e286462ad88cf817ec645c5749f0aa445fd6539`。静态清点：**90 个 `functions` 键、156 个 `fields` 键**，含 `battle_core_update`、`logic_command_parse`、`logic_command_append`、`battle_snapshot_encode`、`battle_snapshot_load`、`replay_stock_restore`。记录的指纹尚未与独立获取的原生二进制重新计算对照。
- [`vendor/crx/env.py`](https://github.com/ak1NaN/Clashback/blob/45c1f26b942ae1d706f2004791e73013e4330099/vendor/crx/env.py) 的 `CrxEnv` 使用 `boot.boot` 加载本地原生库、用 `bindings.of(self.g)` 选择构建映射；`create_match` 经 `G3.load_replay` / `G3.start_battle` 建局；`step(ticks)` 经 `_advance` 调用 `G3.step(self.g,self.state,1)`；`observe` 从内存读取玩家、手牌/循环、战场对象、结果；`queue_card_at`、`queue_hand_action_at`、`queue_ability_action_at` 按未来 Tick 排队。`_inject` 使用原生 `logic_command_parse` 与 `logic_command_append` 将操作写入战斗命令队列。队列进入原生命令流程，但并不能静态保证每个事件实际被战斗接纳。
- [`neo_replay/native_snapshots.py`](https://github.com/ak1NaN/Clashback/blob/45c1f26b942ae1d706f2004791e73013e4330099/neo_replay/native_snapshots.py) 的 `NativeSnapshotStream` 使用原生 `battle_snapshot_encode` / `battle_snapshot_load`、`replay_stock_restore` 实现同一有效战斗内的序列化和恢复，`build` 将每 Tick 快照存储在磁盘并检查最后观测摘要。显式支持的构建集合为 `{160402020,160635001}`。恢复还受引擎绑定、回放摘要、状态代际、拥有线程与渲染监听约束。

## 版本和反证边界

- [`README.md`](https://github.com/ak1NaN/Clashback/blob/45c1f26b942ae1d706f2004791e73013e4330099/README.md) 记载使用 **macOS 14.4+、Apple Silicon、Rosetta 2、x86_64 Python**，原生构建 `160635001`，同步资源版本 `16.635.8`。这是**两个版本维度**，并非 16.635.8 的每个卡牌形态都已验证。
- [`updater/profiles/observed-160635001.json`](https://github.com/ak1NaN/Clashback/blob/45c1f26b942ae1d706f2004791e73013e4330099/updater/profiles/observed-160635001.json) 的文件清单可见 `csv_logic/characters/giant.toml`，但**没有 `csv_logic/characters/giant_ev1.toml` 这一精确文件名**；同清单中的 `electro_giant_ev1.toml` 是另一形态——觉醒雷电巨人，而非普通觉醒巨人 `Giant_EV1`。这只说明该清单未提供对应独立文件的直接证据；不能据此证明该觉醒形态必然缺失（也可能由其他表或热更新定义）。本仓库未发现 `Giant_EV1` 的具体原生部署、半血狂暴区域及快照回归测试。
- [`neo_replay/native_worker.py`](https://github.com/ak1NaN/Clashback/blob/45c1f26b942ae1d706f2004791e73013e4330099/neo_replay/native_worker.py) 对导入的 RoyaleAPI HTML 推断隐藏的起手、随机种子和时间基准，终局核对出牌数/塔 HP 等有限可观测指标；`report` 明说这些指标相等不建立每帧一致。
- `create_match` 的进程内重复建局走 `_restart`；`native_worker.calibrate` 的注释明确提到该 Mac 上上游的进程内重启会崩溃，故通过独立进程重新校准。**不能凭 `create_match` 方法存在就宣称支持稳定高速 reset**。
- 未取得原始 APK/libg 校验输出、完整可运行环境、原生快照可恢复全部外部调度状态的测试、第三方 Windows/Linux 的适配结果或源码授权许可证；也没有独立运行回放。源码存档存在、可定位接口和作者报告的运行经验须分开。

## 对下一步复盘器接入的具体要求

1. 先在匹配 `160635001` + `16.635.8` 资源的授权环境运行最小建局／1 Tick／双方出牌／战斗终止；记录 libg SHA 和每一步结果，重复新建多场尤其要检查进程崩溃。

3. 专项验证 `Giant_EV1` 能否被这个具体资源包加载：先解析形态清单，再提交部署动作，逐 Tick 核对半血触发、狂暴半径变化和快照重放。单独保留失败样本。
4. 对 Windows 的需求，优先核对 x86_64 本地加载器/Bionic 兼容层与渲染依赖，不能把 macOS + Rosetta 的运行路径视为 Windows 现成安装包。
