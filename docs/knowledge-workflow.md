# 技术知识生命周期与复用规范

中台管理的核心不是 Markdown 文件数量，而是**可追溯且能够在新工程问题中再次应用的知识**。

## 研究资料如何成为可用知识

```text
具体技术问题
    ↓
检索来源（README / 代码 / 测试 / 实验 / 已知失败）
    ↓
拆成可核对的原子结论 + 来源锚点
    ↓
核对作用域、证据等级、反例、未解决假设
    ↓
跨来源综合：共同机制 / 差异 / 有条件的推论
    ↓
映射到能力与技术专题，补验证方法
    ↓
被新项目使用并反馈失败/成功，更新适用范围
```

**原始材料**不自动成为结论；**作者的主张**不自动成为事实；**静态源码存在**不自动成为可运行组件；**多份资料都这样写**也不自动构成独立验证。

## 四类知识对象与存放位置

| 类别 | 内容及用途 | 主位置 |
| --- | --- | --- |
| **来源事实** | 具体字段、接口、机制观察，绑定来源、版本和证据状态 | `registry/reverse-findings.yaml`、源码审计、`research/` |
| **机制知识** | 解释为什么成立，包含必要条件、状态变化与反例 | `topics/`、`research/knowledge-notes/` |
| **工程判断** | 对同一问题比较路线、复杂度、限制与可复用条件 | `capabilities/`、`landscape/` |
| **实施知识** | 操作约束、适配方式、最小验收场景、可复现失败 | `guides/`、`contracts/`（Draft）、测试记录 |

这四类是**内容职责**，不是新增四个 YAML 数据实体。已有 Project、Capability、Implementation、Topic、ReverseFinding 继续作为机器索引的单一事实源。不要为了知识管理形式化额外复制索引数据。

## 技术主张的质量门槛

一条独立技术结论至少应包含：

1. **命题**：主张什么？是否足够具体以被反证？
2. **来源**：谁发现的，哪一仓库/提交/文件/测试？什么时候查过？
3. **适用域**：游戏构建、资源版本、ABI、Tick、坐标、平台、观测权限；与结论无关的维度可以省略。
4. **证据状态**：作者文档、静态源码、独立实验，或未知，不能跨级推断。
5. **反例和限制**：哪些场景不成立、没有检测过、版本改变后需要复验？
6. **工程价值**：怎样影响开发者的选型、适配、测试或研究？

若材料还不能支持技术结论，记录为**待查线索**，不要为了产出文档而强行总结一个规律。

## 三种常见错误及纠正

| 错误知识 | 正确做法 |
| --- | --- |
| “FirstLight 支持快照，所以能直接并行 MCTS。” | 记录其进程内句柄生命周期；并行搜索还需实例隔离和克隆成本实验 |
| “RoyaleSim 和 FirstLight 都能 step，可以互换。” | 核查动作 schema、Tick、观测范围、游戏规则及环境依赖 |
| “某个内存 offset 已经找到了。” | 绑定精确 `libg.so` 和客户端构建，附验证方法；新版本先复验 |

## 什么时候更新已有知识

- **来源更新**：判断旧结论是否仍适用，增加版本记录，不静默覆盖历史值。
- **出现相反实验**：将冲突写在原结论附近，更新“已知反例/未知”，保留证据；必要时降低成熟度。
- **派生的实施失败**：将失败反向记录到适配限制、机制知识和验收用例。
- **多源归纳成熟**：由 `topics/` 归纳机制，再以任务形式更新 `capabilities/`；不制造第二份机器实现矩阵。
- **知识失效**：标为历史或失效，不必删除仍有研究价值的发现。

## 角色分工

[research-cr-knowledge](../.agents/skills/research-cr-knowledge/SKILL.md) 负责搜集和拆解证据；[synthesize-cr-knowledge](../.agents/skills/synthesize-cr-knowledge/SKILL.md) 负责多源归纳；[apply-cr-knowledge](../.agents/skills/apply-cr-knowledge/SKILL.md) 负责用知识回答开发问题；[curate-cr-knowledge](../.agents/skills/curate-cr-knowledge/SKILL.md) 负责写回索引；[review-cr-evidence](../.agents/skills/review-cr-evidence/SKILL.md) 负责质量审查。

只在能形成独立、可重用技术解释时创建知识笔记。一个问题若已经在能力卡或专题讲清楚，优先编辑原页面。
