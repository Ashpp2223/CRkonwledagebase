# 技术知识文档写作规范

## 写什么

让读者用最短路径了解：**技术问题、已有做法、适用条件、证据、未完成事项和复用选择**。标题描述真实主题；正文优先事实、精确术语和可定位的源码/测试。

## 必须区分

- **Author-documented**：上游作者的说明；用“作者文档记载/报告”，不等于中台验证。
- **Source-inspected**：指定 Git SHA 的源码实现已静态检查；不把存在函数视为功能运行成功。
- **Reproduced**：记录真实测试环境、执行过程、日志和结果；失败也可为高价值证据。
- **Unknown**：缺少信息，保持未知，不通过推测补字段或把估算当作精确事实。
- **R0–R4** 表示单个项目的单项能力的复用准备程度，不是所有项目通用准确度排名。

## 表达习惯

- 默认中文正文；上游类名、路径、协议字段保留原名，必要时首次解释。
- 用“支持的构建”和“最近核查日期”替代“目前/最新/全部兼容”等易过时措辞。
- 重要事实链接至固定提交与文件位置；外部来源不能替代实际独立实验。
- 将**接口签名、运行环境、行为语义、性能数据和版权授权**分别记录。
- 构建、资源表、ABI、Tick 单位、坐标和可见性存在版本依赖时明确声明；并不要求在每个段落重复整段警示。
- 研究存在矛盾时先解释不同版本与实验设置，再表达结论；不得用假精度统一各种数据。

## 避免文档噪声

- 不反复解释仓库**不是什么**，不插入与技术任务无关的组织、项目或作者关系声明。
- 不复述每个贡献者都已在其他页面看到的口号、免责声明和“未来愿景”。
- 不把 README 的宣传式性能描述改写成已独立验证的成绩；没有确认的指标直接标“作者报告/未核实”。
- 不为每个实现机械套用冗长固定格式；真实复杂度决定文档长度。
- 禁止为增加篇幅而建立空目录、空章节和无差别罗列的仓库名单。
- 仅保留影响复用决定的限制：版本、证据、许可、资源来源与失败模式。

## 维护时更新哪些位置

| 变更 | 应更新 |
| --- | --- |
| 发现新的项目实现 | 项目/能力登记与关键入口，不必复制作者全部 README |
| 原作者修复 bug | 相关版本对应的能力卡、适用范围和来源 |
| 新的逆向发现 | 发现登记、研究正文、正例/反例和影响的能力 |
| 下游接入成功 | 实施记录、固定构建、实测日志、成熟度评级 |
| 技术路线有争议 | 对照表与证据，不创建没有事实依据的优劣排名 |

规范更新遵循实际需要，不为文风小改动追求全仓重写。
